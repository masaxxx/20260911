# trend-sourcing.md — Xの時事ネタを集めて裏取りする

安全判定の正本は [guardrails.md](guardrails.md)。ここの除外ゲートは見出しだけで落とす一次フィルタで、同じ R コードを使う（検索レシピ S1〜S8 は別物）。日付はすべて JST の基準日（SKILL.md Step 0）。実測ログは [background.md](background.md) §5。

## 0. フロー

```
[Tier 0] 話題の指定あり → ゲート → 裏取り（§2）
[Tier 1] X_BEARER_TOKEN あり → X API（§3）
[Tier 2] アグリゲータへ WebFetch（1回だけ試す。§4）
[Tier 3] WebSearch レシピ（クラウドでは主力。§5）
[Tier 4] ユーザーに聞く（対話モードで、選べる候補が3件未満のときだけ）
どの経路も: 生の候補 → 除外ゲート → 裏取り → 候補リスト → 1件選ぶ
```
- 目標は**選べる候補6〜12件**、検索予算は**20〜25回**。届かなくても予算を使い切ったら進み、ヘッダーに件数を書く。件数より裏取りの質を優先する。
- Tier 4 では、トレンド画面のスクショか気になるワード3〜5個を頼む。スクショに RED が写っていても書き起こさない。

## 1. 除外ゲート

- 見出しを読んだ時点で R1〜R10（guardrails.md §1）を当てる。当たったら、追加の検索・要約・URLの保存をしない。
- 見出しで当たりやすいもの: R1 人名＋流出・合成・性的なうわさ／R2 死傷・自殺・闘病・著名人の死・負傷の有無が不明な事故／R3 未成年／R4 一般人や小規模な個人クリエイターの炎上・晒し／R5 公式発表のない疑惑や障害の投稿／R6 属性でくくるバズ／R7 逮捕・送検・薬物騒動／R8 実在人物のAI合成がネタの中心／R9 進行中の災害・戦争。R10 と Y6（選挙期間中）は選定時に判定する。
- NG語（流出・裸・ディープフェイク・不倫相手など）と人名を組み合わせたクエリは作らない。
- 標的を限定して載せるもの: 公人・大企業の公的な言動（不正をでっち上げない）／企業トラブル（被害を受けた利用者は笑わない）／スポーツ（プレーと采配だけ）。
- ネガティブでない未確認の話題は RED ではない。裏取りに回し、取れなければ落選。

## 2. Tier 0 — 指定あり

- 話題の指定: ゲート（RED なら guardrails.md §6）→ `<固有名詞> <出来事の名詞>` の中立的なクエリで1〜2回 → 古くても指定なら可（`[古い:ユーザー指定]`）。裏取りが取れなければそう伝え、事実として扱わない。
- カテゴリ・期間だけの指定（「今週の政治か値上げ」）: S1・S2 はカテゴリ語を足さずに回し（足すと0件になる）、後で絞る。狙った検索を1〜2回足す（政治 → S4 で `閣僚 発言 撤回`、値上げ → `値上げ 発表 SNS 反応`）。「AかB」はどちらでもよい。言われた期間は鮮度ラベルより優先する。解釈をヘッダーに1行書く。

## 3. Tier 1 — X API（ローカル向け・未検証）

- 2026-10 のクラウドでは未設定で、api.x.com は 403。仕様と料金は https://docs.x.com/ で確認する。
- トークンは有無だけ確認し、値は表示しない: `[ -n "$X_BEARER_TOKEN" ] && echo set || echo unset`
- トレンド: `curl -sS --max-time 20 -H "Authorization: Bearer $X_BEARER_TOKEN" "https://api.x.com/2/trends/by/woeid/23424856?max_trends=50"`
- 直近の投稿（有料プラン・7日分）: `https://api.x.com/2/tweets/search/recent` に `query=<語> lang:ja -is:retweet`。投稿はバズの証拠（C）としてだけ使う。
- 401・403・429・HTTP 000 なら Tier 2／3 へ。

## 4. Tier 2 — アグリゲータ

- `WebFetch https://trends24.in/japan/` を1回だけ試す。ENOTFOUND・403・タイムアウトなら Tier 2 全体を諦める（クラウドではほぼ遮断）。
- 届くなら trends24.in/japan、getdaytrends.com/japan、search.yahoo.co.jp/realtime、jp.trend-calendar.com を読む。prompt は「要約せず、語・順位・時刻を列挙」。
- トレンド語は1語につき1回の WebSearch で文脈を調べてからゲートに通す。語そのものが人名＋NG語なら、調べずに R1。

## 5. Tier 3 — WebSearch

### 5-1 方針
- 探索は `mode: "extended"`、裏取りは `"standard"`。日付は見出しの書き方に合わせる。対象は今日・昨日・一昨日。
- `allowed_domains` にクローラー拒否ドメインを入れると検索全体が 400 エラーになる（確認済: hochi.news、nikkansports.com、sponichi.co.jp、huffingtonpost.jp）。エラーに出たドメインを外して再実行する。
- Links のタイトルがドメイン名だけなら、同じクエリを `allowed_domains` にそのドメインだけを入れて1回再検索する（記事タイトルと日付入りURLが出やすい）。出なければタイトルは「（タイトル未取得）」とし、要約から補わない。
- 記事本文の WebFetch は計1回まで試す。ENOTFOUND なら以後は試さない。

### 5-2 当たりレシピ

| ID | クエリ | パラメータ | メモ |
|---|---|---|---|
| S1 | `SNSのバズまとめ (YYYY/MM/DD)`／`SNSのバズまとめ 批判 物議 (YYYY/MM/DD)`／`Yahoo!リアルタイム検索 バズまとめ M月` | `allowed_domains: ["search.yahoo.co.jp"]`, extended | ◎ 1回で約10件。AI要約なので発見専用（5-3） |
| S2 | `"YYYY年M月D日掲載" ネット 声`／`"YYYY年M月D日掲載" SNS 話題` | extended | ◎ ライブドアの当日記事 |
| S3 | `"M月D日" SNS 話題 投稿 反響` | extended | ○ |
| S4 | `物議 ネット 賛否 YYYY年M月` | `allowed_domains: ["news.livedoor.com","news.infoseek.co.jp","news.yahoo.co.jp"]`, extended | ◎ |
| S5 | `炎上 SNS 反発 声`／`ネットで話題 物議` | `allowed_domains: ["j-cast.com"]` | ○ 古い記事が混ざる。URLの年月で選ぶ |
| S6 | `YYYY/MM/DDの話題ツイートまとめ` | `allowed_domains: ["posfie.com","togetter.com"]` | ○ バズの証拠（C）だけ |
| S7 | `"M月D日" X トレンド入り` | extended | ○ トレンドのスナップショット |
| S8 | `話題 注目集める M月` | `allowed_domains: ["x.com"]`, extended | △ 日付が混在 |

外れ: 曖昧な月指定（`Xで話題 2026年10月`）／英語の汎用クエリ（アダルト系スパムが出る）／URL文字列のクエリ／英字・カタカナだけの裏取りクエリ。

### 5-3 Yahoo!「SNSのバズまとめ」の注意
- 本文は生成AIの要約。実測では8件中4件が報道・公式で確認できなかった。**何がバズっているかを知る発見用**に限り、事実の根拠にしない。
- URL末尾の10桁は作成時刻の Unix 秒: `TZ=Asia/Tokyo date -d @<10桁> '+%F %H:%M'`。

### 5-4 実行順
1. 探索（約8回）: S1 を今日・昨日・一昨日で3回、S2 を今日・昨日で2回、S4・S5・S6 を各1回。
2. 生の候補をゲートに通す。
3. 笑いの伸びしろが大きい順に、1件1回で裏取りする（約10〜14回）。見込みの薄い話題に予算を使わない。
4. 選べる候補が6件未満で予算が残っていれば、S3・S7・S8 で補う。

## 6. 裏取りと鮮度

### 6-1 ソースのクラス
- **A 一次情報**（公式発表・公式アカウント）／**B 報道**／**C X上の反応の集約**（バズまとめ・posfie・Togetter・トレンド系サイト・X投稿）。C はバズの証拠で、事実の根拠にならない。ただし事実行で「〜という話題がXで広がっています」とバズの中身を言う根拠にはなる（『』なし・一般人を出さない・実在の人物・企業のネガティブを含まない）。
- 転載（Yahoo!ニュース・ライブドア・Infoseek など）は元媒体で数える。元媒体が分からない転載は独立の1件に数えない。共同通信の配信で複数紙に載ったものは1件。同じ媒体の複数記事は1件。コラムは出来事の確認に数えない。C どうしは独立した2件にならない。

### 6-2 証拠の強さ
本文（WebFetchで読めた）＞ リンク（Links のタイトル＋URL）＞ 要約（検索結果の要約文。年の取り違えや混同がある）。出来事の核（何が起きたか）は、本文かリンクで確かめる。

### 6-3 判定

| 判定 | 条件 |
|---|---|
| **確認済** | GREEN・中立の話題: 信頼できる A/B が1件（本文かリンク）。実在の人物・企業の**ネガティブな出来事**（不祥事・炎上・失言・事故・トラブル）: 独立した A/B が2件以上。公式発表そのものが出来事（発売・価格・ダイヤ・天気の記録など）なら A 1件 |
| **確認済（要約ベース）** | WebFetch不可の環境では、独立した2媒体の検索要約が一致し、かつ Links にその媒体のURLが出ていれば「確認済（要約ベース）」とし、台本では「〜と報じられています」と書き、公開前確認TODOに入れる |
| **条件付き** | C でバズは確認できたが、A/B は背景情報だけ。ミームや考察ブームのような「現象」なら選べる。実在の人物・企業の言動が核なら選ばない。中立の事実が A/B で確認済みで、新しいのが C のバズだけなら確認済とする |
| **未確認** | C だけ／食い違い／URLなし。ネガティブでなければ落選、ネガティブなら R5（コードだけ） |

- 核は確認済みで、細部（数値・文言）が要約にしか出ないとき: 別々の検索2回の要約で一致すれば【要約一致】として「報道では」と添えて使い、公開前TODOで照合する。要約どうしが食い違うもの、ネガティブな主張、『』で引く企業・人物の言葉、核が条件付きの回には使わない。帰属は「報道では」で言い、企業の案内・公式の言葉にしない（guardrails.md §3）。
- 公人の公的発言への批判は、発言そのものが確認できれば足りる。

### 6-4 日付と鮮度
- URLの日付、タイトルの日付、Yahoo!まとめの Unix 秒を見る。要約文だけにある日付は証拠にしない。毎年の行事（CS・ドラフト・紅白・M-1・ハロウィン・ノーベル賞など）は、去年の記事が先に出やすい。
- `[新鮮]` 初出が72時間以内／`[継続]` 初出が3〜7日前で、72時間以内に新しい展開がある／`[古い]` それ以外（選べない。Tier 0 の指定と、言われた期間の中は例外）。

## 7. 記録と候補リスト

### 7-1 記録
- この回の WebSearch／WebFetch の出力に実際に出たURLだけを記録する。推測したり組み立てたりしない。
- 1行の型: `- [B] 媒体（元: 元媒体） | YYYY-MM-DD | タイトルそのまま | URL | 取得日 / 経路 / 本文・リンク・要約`。実在の人物・企業について未確認のネガティブな語を含むタイトル（C に多い）は「（タイトル省略）」と書く。
- 保存先は `<出力先>/candidates/YYYY-MM-DD-candidates.md`（同じ日の2回目以降は `-2` など）。

### 7-2 一覧表
```markdown
## 時事ネタ候補（基準日 YYYY-MM-DD JST / 経路: Tier N / 検索 NN 回 / 選べる候補 N 件）
| # | トピック | なぜバズってる（1文） | 日付（初出→最新） | 鮮度 | 裏取り | 安全 | 裏の物語の角度 |
|---|---|---|---|---|---|---|---|
| 1 | … | … | 10/05→10/12 | 新鮮 | 確認済 B×2 | YELLOW(Y2) | … |

RED: R2×n, R4×n
落選（コードのみ）: Y4×n
落選: 〇〇（理由: 未確認）、…
```
- 1件ごとの詳細: なぜバズってる（事実だけ）／日付と鮮度／ソース（7-1の型）／裏取りの判定／安全（誰を刺し、誰を刺さないか）／初期の角度（黒幕は架空、実在の固有名詞なし。「何のギャップに笑っているか」を1語で）。
- 並べ順: 選べる候補を SKILL.md Step 3 の点数順 → 中立の落選 → コードのみの行。

### 7-3 除外・落選ログ
- **RED**: コード×件数だけ（`RED: R2×1, R4×2`）。名前・URL・内容・一般化した説明も書かない（「被害を受けた利用者が近い」のような理由も書かない）。実在の人物・企業の未確認のネガティブ情報（炎上・批判・障害・漏えい）は R5 でここへ。
- **実在の人物・企業にとってネガティブになりうる話題**（確認済みでも、選ばなかったもの）と、**実在の個人の本業以外の話題**（映り込み・進退など）: コード×件数だけ（`落選（コードのみ）: Y2×1, Y4×1`）。
- **複合ネタ**: 一覧・詳細・返答は、安全な部分（guardrails.md §1 STEP 3）だけで書く。未確認のネガティブ部分（「炎上した」「批判された」）を断定で残さない。
- **中立の落選**（未確認・古い・伸びしろ不足）: 話題名と理由を書いてよい。理由に健康・私生活の推測は書かない。
