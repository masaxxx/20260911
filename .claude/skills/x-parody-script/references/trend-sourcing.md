# trend-sourcing.md — 時事ネタ（X/日本）収集手順

このファイルは「Xで今バズっている日本の時事ネタ」を集め、実在と鮮度を確かめ、**パロディ脚本の候補リスト（10〜15件）**として出すまでの手順書。脚本を書く前に必ずこの手順を通す。

- 安全判定の正本は [guardrails.md](guardrails.md)（Q1〜Q10 のハードストップと RED / YELLOW / GREEN 判定）。本ファイルの「除外ゲート」（A〜H）は、**集めた直後に素早く落とすための一次フィルタ**で、guardrails.md の RED コードに対応している（1-1 の表の右端の列）。
- 検索レシピの ID は **S1〜S8**（Search の S）。guardrails.md の RED コード R1〜R10 と混同しないこと。

---

## 0. 全体フロー

```
[Tier 0] ユーザーが話題を指定済み？ ──yes──▶ 除外ゲート → 裏取り → 候補1件として確定
        │no
        ▼
[Tier 1] X_BEARER_TOKEN あり かつ api.x.com に届く？ ──yes──▶ トレンド取得＋recent search
        │no / 失敗
        ▼
[Tier 2] アグリゲータに WebFetch が届く？（1回だけ試す） ──yes──▶ trends24 / getdaytrends / Yahoo!リアルタイム
        │no（ENOTFOUND / 403）
        ▼
[Tier 3] WebSearch レシピ（日付アンカー付き）  ← クラウド環境では実質ここが主力
        │候補が 5 件未満
        ▼
[Tier 4] ユーザーに聞く（トレンド画面のスクショ・気になるワード）※非対話（サブエージェント）実行時は聞かずに手元の候補で進む

どの経路でも：生の候補 → ★除外ゲート → 裏取り（2ソース・日付） → 候補リスト出力 → 1件選ぶ
```

- **除外ゲートはすべての Tier で、集めた直後・追加の検索をする前に**通す。ゲートで落ちた話題には、それ以上何もしない（調べない・URLを残さない・別の角度も考えない）。
- 目標は「選べる候補（裏取りが確認済みか条件付き）を 10〜15 件」。未確認のものも、落選理由が分かるようにリストの下に残してよい。

## 1. 除外ゲート（★必須・構造的に防ぐ）

### 1-1. 絶対NG（候補に載せない、深追いもしない）

| コード | カテゴリ | 例（一般化した書き方） | guardrails.md |
|---|---|---|---|
| A | **実在人物の性的な噂・「流出動画/流出画像」・ディープフェイク・リベンジポルノ・性的な合成**（真偽は問わない。「デマだと笑う」形でも不可） | 「〇〇の流出動画」「〇〇似のAV」「〇〇 ディープフェイク」 | R1（＋R8） |
| B | 未成年が関わる性的・恋愛的な話題、未成年の一般人 | 中高生の妊娠告白、学生の晒し | R3 |
| C | 死亡・重傷の事件事故、災害・自殺。被害者・遺族が特定できるもの | 祭りの死亡事故、殺人事件、大事故 | R2 / R9 |
| D | 私人（一般人）や小規模な個人クリエイターを標的にする炎上・晒し・嘲笑 | 一般人の失言の晒し、個人VTuberのアカウント凍結を嘲笑する流れ | R4 |
| E | 実在人物に未確認の犯罪や不正の疑いをかける噂。薬物・刑事事件に関わる個人 | 逮捕前の「〇〇が××したらしい」、薬物騒動の当事者 | R5 / R7 |
| F | 実在人物のAI合成動画や偽画像そのものがネタの中心になっているもの | 政治家の「若返り」AIダンス動画 | R8 |
| G | 人種・国籍・民族・障害・性的指向・宗教・性別など属性でくくるもの（ブラックジョークにするとステレオタイプになる） | 「〇〇人は〜」系のバズ | R6 |
| H | 戦争・テロ・虐殺の犠牲 | ドローン攻撃、空爆被害 | R9 |

- このゲートを通過した候補にも、選定時に guardrails.md §1 の Q1〜Q10 を改めて当てる（R10＝実在人物・団体への暴力オチ、Y6＝選挙運動期間中の候補者ネタ などはここでは拾いきれないため）。

### 1-2. ゲートの運用ルール

1. **生の見出しを読んだ時点で判定する。** NGに当たったら、その話題について追加の WebSearch や WebFetch を**しない**。
2. **NGの語を検索クエリに入れない。** 実在人物の名前と「流出」「動画」「裸」「ディープフェイク」「AV」「不倫相手」などを組み合わせたクエリは絶対に作らない。
3. 除外ログには**カテゴリコードと件数だけ**を残す（A・B は話題の中身も書かない）。例: `除外: A×1, C×1, D×2`
4. **Tier 0 でユーザーが NG 話題を指定した場合**: その話題では書けないことを1〜2文で伝え、理由は「実在の人を性的に扱う／被害者を笑うことになる」程度に留める。そのうえで Tier 3 の候補リストを代わりに出す。NG話題を言い換えて続けない（人物名を伏せる、「デマを笑う」形にする、似た架空人物を立てる、といった抜け道も使わない）。
5. **要注意（載せてよいが標的を限定する）**:
   - 政治家・大企業・有名人の**公的な言動**: 権力側を刺すのは可。現実と取り違えられるような具体的な不正をでっち上げるのは不可。
   - 情報漏えいや障害などの企業トラブル: **企業・制度・犯人側**を笑う。被害を受けた利用者は笑わない。
   - スポーツ選手のプレーや采配: プレーや采配はいじってよい。容姿・家族・私生活はいじらない。

## 2. Tier 0 — ユーザー指定の話題

1. 除外ゲートを通す（上の 1-2 の4）。
2. 次のような**中立的なキーワード**で WebSearch を1〜2回し、事実関係と日付を押さえる: `<固有名詞> <出来事の名詞>`（例: `タイムズカー 免許証 流出 パーク24`）。
3. 鮮度（7-4）が「古い」でも、ユーザーが望むなら進めてよい。その場合は候補表に `[古い:ユーザー指定]` と明記する。
4. 裏取りが取れない（噂しかない）なら、そう伝える。出来事を事実として扱う脚本にはしない。

## 3. Tier 1 — X API v2（環境変数 `X_BEARER_TOKEN` があるとき）

> **注意**: 2026-10-12 時点のクラウド環境では、トークンは未設定で、`api.x.com` への接続もプロキシに 403 で拒否された（`curl: (56) CONNECT tunnel failed, response 403`）。このためこの手順は未検証。ローカル実行時に使う。**エンドポイント・料金プラン・レスポンス形式は変わりやすいので、使う前に必ず https://docs.x.com/ の最新ドキュメントで確認すること。**

### 3-1. 事前チェック（トークンの値は絶対に表示しない）

```bash
[ -n "$X_BEARER_TOKEN" ] && echo "X token: set" || echo "X token: unset"
```

### 3-2. 日本のトレンド（WOEID 23424856）

```bash
curl -sS --max-time 20 -w '\nHTTP %{http_code}\n' \
  -H "Authorization: Bearer $X_BEARER_TOKEN" \
  "https://api.x.com/2/trends/by/woeid/23424856?max_trends=50"
# 期待される形（要確認）: {"data":[{"trend_name":"#...","tweet_count":12345}, ...]}
# 整形:
#   ... | jq -r '.data[] | [.trend_name, (.tweet_count // "")] | @tsv'
```

- 旧 v1.1 の `https://api.twitter.com/1.1/trends/place.json?id=23424856` は、新しいプランでは使えないことが多い。v2 が使えないときに試す程度でよい。

### 3-3. 直近の投稿検索（バズの規模と文脈の確認用）

```bash
curl -sS --max-time 20 -G "https://api.x.com/2/tweets/search/recent" \
  -H "Authorization: Bearer $X_BEARER_TOKEN" \
  --data-urlencode 'query=シャウエッセン lang:ja -is:retweet' \
  --data-urlencode 'max_results=50' \
  --data-urlencode 'sort_order=relevancy' \
  --data-urlencode 'tweet.fields=created_at,public_metrics' \
| jq -r '.data[]? | [.created_at, .public_metrics.like_count, .public_metrics.retweet_count, (.text|gsub("\n";" ")|.[0:80])] | @tsv'
```

- recent search で取れるのは**直近7日分だけ**で、**有料プラン（Basic 以上、または従量課金のクレジット）が必要**（料金体系は要確認）。無料枠ではほぼ使えない前提で考える。
- 投稿本文は**バズの証拠（Cクラス）**としてだけ使う。事実の裏取りは報道や公式発表で取る。
- 除外ゲートで落ちた話題の語を、この検索のクエリに入れない（1-2 の2）。

### 3-4. 失敗の切り分け

| 症状 | 意味 | 対応 |
|---|---|---|
| `curl: (56) CONNECT tunnel failed, response 403`／`HTTP 000` | 環境のネットワークポリシーで遮断されている | Tier 1 を諦めて Tier 2/3 へ |
| `HTTP 401` | トークンが無効 | ユーザーに伝え、Tier 2/3 へ |
| `HTTP 403`（JSON本文あり） | プランにこのエンドポイントが含まれない | Tier 2/3 へ |
| `HTTP 429` | レート制限 | 待たずに Tier 2/3 へ |

## 4. Tier 2 — アグリゲータを WebFetch で読む（届く環境のみ）

### 4-1. まず1回だけ試す

`WebFetch https://trends24.in/japan/` を1回だけ試す。エラーが `getaddrinfo ENOTFOUND`、403、タイムアウトのどれかなら、**この Tier 2 は全体を「使えない」とみなし、以降のアグリゲータへの WebFetch はしない**（1サイトずつ試して時間を無駄にしない）。

> 2026-10-12 クラウド実測: 下表のサイトはすべて WebFetch で `getaddrinfo ENOTFOUND` になった。curl は `CONNECT tunnel failed, response 403` だった。ローカルの Claude Code なら届く可能性が高い。

### 4-2. 届く場合の取得先（優先順）

| # | URL | 取れるもの | WebFetch に渡す prompt の例 |
|---|---|---|---|
| 1 | https://trends24.in/japan/ | 1時間ごとの日本のXトレンド（直近24時間） | 「直近3時間分のトレンド語を順位と時刻つきで、要約せずそのまま列挙」 |
| 2 | https://getdaytrends.com/japan/ | 現在のトレンドと投稿数 | 同上＋「投稿数も」 |
| 3 | https://search.yahoo.co.jp/realtime | Yahoo!リアルタイム検索のトレンド（Xの投稿がもとになっている） | 「トレンドのキーワードを順位どおりに」 |
| 4 | https://search.yahoo.co.jp/realtime/search/matome | 「SNSのバズまとめ」（日付入りのAI要約） | 「見出しと日付を全部」 |
| 5 | https://jp.trend-calendar.com/ （日別は `trend/YYYY-MM-DD.html`） | Xトレンドの日別アーカイブ | 「その日のトレンド語を順位つきで」 |
| 6 | https://www.itmedia.co.jp/news/subtop/nettopics/ | ITmedia「ネットの話題」 | 「見出しと日付」 |
| 7 | https://news.yahoo.co.jp/ranking/access/news | アクセスランキング（事実確認の補助） | 「見出しと媒体名」 |

- 読み取ったトレンド語はそのままでは中身が分からないことが多い（例: 「和田さん」）。**1語につき1回の WebSearch で文脈を調べてから**除外ゲートに通す。ただし、トレンド語そのものが人名＋NG語（「流出」など）の組み合わせなら、文脈を調べずにその場で A として落とす。

## 5. Tier 3 — WebSearch レシピ（クラウドでの主力）

### 5-1. 基本方針

- 探すときは `mode: "extended"`、裏取りのときは `mode: "standard"` を使う（日付を指定したクエリは extended の方が新しい結果をよく拾った）。
- **日付は「サイトの見出しの書き方」に合わせて入れる**（下の表）。「2026年10月」のような曖昧な月指定はゴミを呼ぶ。
- 対象日は **今日・昨日・一昨日**（72時間）。S1 と S2 をそれぞれの日付で回す。
- 証拠として使うのは、WebSearch の要約文ではなく **Links に出たタイトルと URL**。要約文は年を取り違えたり混ぜたりする。
- `allowed_domains` に**クローラーを拒否しているドメインを1つでも入れると、検索全体が 400 エラーになる**。2026-10-12 時点で確認したのは `hochi.news` `nikkansports.com` `sponichi.co.jp` `huffingtonpost.jp`。エラーメッセージに出たドメインを外して再実行する。

### 5-2. 当たりレシピ（効果の高い順）

| ID | クエリの型 | パラメータ | 実測（2026-10-12） |
|---|---|---|---|
| **S1** | `SNSのバズまとめ (YYYY/MM/DD)`／`SNSのバズまとめ 批判 物議 (YYYY/MM/DD)`／`Yahoo!リアルタイム検索 バズまとめ M月` | `allowed_domains: ["search.yahoo.co.jp"]`, extended | ◎ 10/09〜10/12 のまとめが1回あたり約10件。タイトルに `(2026/10/12)` 形式の日付がある。**ただしAI要約なので裏取りが必須**（5-4） |
| **S2** | `"YYYY年M月D日掲載" ネット 声`／`"YYYY年M月D日掲載" SNS 話題` | extended | ◎ ライブドアニュースの当日記事がまとめて出る（タイトルに掲載日あり）。NG話題も混ざるのでゲートに通す |
| **S3** | `"M月D日" SNS 話題 投稿 反響` | extended | ○〜◎ ライブドア・Yahoo!まとめ・Infoseek が混ざって出る |
| **S4** | `物議 ネット 賛否 YYYY年M月` | `allowed_domains: ["news.livedoor.com","news.infoseek.co.jp","news.yahoo.co.jp"]`, extended | ◎ 10/5〜10/12 の炎上・物議系と、ライブドアのキーワードまとめ（「炎上・批判【10/10更新】」）が出る |
| **S5** | `炎上 SNS 反発 声`／`ネットで話題 物議` | `allowed_domains: ["j-cast.com"]` | ○ 新しい記事（URLが `/2026/10/..`）と2017〜2023年の古い記事が混ざる。**URLの年月で選別する** |
| **S6** | `YYYY/MM/DDの話題ツイートまとめ`／`話題 まとめ YYYY年M月` | `allowed_domains: ["posfie.com","togetter.com"]` | ○ posfie の日別まとめ（ユーザー作成）や `togetter.com/YYYY/MM/DD` の日別アーカイブ。バズの証拠（C）としてのみ使う |
| **S7** | `"M月D日" X トレンド入り` | extended | ○ trend-calendar のスニペットに「2026/10/12 00:00 更新」時点のトレンド語（#VIVANT など）が出た。Googleトレンドや ranknavi のスナップショットも出る |
| **S8** | `話題 注目集める M月` | `allowed_domains: ["x.com"]`, extended | △ `x.com/i/trending/<id>`（X公式のトレンド解説ページ）がインデックスされている。日付が混在するので要確認 |

### 5-3. 外れレシピ（使わない）

| クエリ | 結果 |
|---|---|
| `Xで話題 2026年10月`／`トレンド入り 10月11日 2026` | 自治体のカレンダーや海外ページなどのゴミ。直近の話題は0件 |
| `"X（旧ツイッター）" 話題 2026年10月11日` | ピクシブ百科事典の編集履歴ばかり |
| `Japan Twitter trending October 2026 viral`（英語の汎用クエリ） | **スパムとアダルト系スパム**。危険なので使わない |
| `j-cast.com/2026/10 話題`（URLを文字列でクエリに入れる） | 効かない |
| `大喜利 X 話題 ハッシュタグ 2026年10月` | 企業の大喜利キャンペーンの告知だけ |
| `SNSで話題`（`allowed_domains: nlab.itmedia.co.jp`） | 一般人の「まさかの〜」系バズ投稿で、日付が不明確。私人ネタなのでパロディには不向き |
| 英字やカタカナが中心の裏取りクエリ（例: `VIVANT ラッピング列車 車と衝突`） | 英語圏の無関係な結果になった。日本語の名詞を足す |

### 5-4. Yahoo!「SNSのバズまとめ」の扱い

- URL 末尾の10桁は **Unix 秒の作成時刻**（実測で、タイトルの日付と全件一致した）。
  ```bash
  TZ=Asia/Tokyo date -d @1791801300 '+%Y-%m-%d %H:%M JST'   # → 2026-10-12 19:35 JST
  ```
- 本文は**生成AIによる要約**。2026-10-12 に裏取りを試した8件の内訳は、報道・公式で確認できたもの2件、一部だけ確認できたもの2件、**確認できなかったもの4件**（金融サービスの誤作動、レース中の事故の内容、アニメのコラボ告知、ミームのフレーズ）。
- したがって S1 は「何がバズっているか」を知るための**発見用**に限る。事実の根拠には使わない。

### 5-5. 推奨の実行順（検索予算 20〜25回）

1. 探索: S1 を今日・昨日・一昨日で計3回、S2 を今日・昨日で計2回、S4・S5・S6 を各1回（**約8回**）。
2. 生の候補（25〜40件）を除外ゲートに通す。
3. 残ったものを1件につき1回、`<固有名詞> <出来事の名詞>` で standard 検索して裏取りする（**約10〜15回**）。
4. 選べる候補が10件未満なら、S3・S7・S8 で補う。

## 6. Tier 4 — ユーザーに聞く

選べる候補が5件未満、または Tier 1〜3 がすべて失敗したときに使う（対話モードのみ）。次のように頼む:

> 「Xのトレンド画面（おすすめ／トレンド／ニュース）のスクリーンショットを貼るか、気になっているワードを3〜5個教えてください。」

- スクショは Read で画像として読み、トレンド語を書き起こす。そのあと Tier 0 と同じ手順（ゲート → 裏取り）に回す。スクショに NG 話題が写っていても、書き起こし・記録しない（コードと件数だけ）。
- 非対話（サブエージェント）実行時は聞かない。手元の選べる候補から選び、それも0件なら SKILL.md の「候補ゼロ時の扱い」に従う。

## 7. 実在と鮮度の確認

### 7-1. ソースの分類

| クラス | 内容 | 例 |
|---|---|---|
| **A 一次情報** | 公式発表、当事者の公式アカウントやサイト | 企業のプレスリリース、公式X |
| **B 報道** | 新聞・通信社・TV・ネットメディア | NHK、共同（地方紙経由）、時事、J-CAST、AdverTimes、オリコン |
| **C X上の反応の集約** | バズの証拠にはなるが、事実の根拠にはならない | Yahoo!リアルタイム「バズまとめ」、`x.com/i/trending`、posfie/Togetter、trend-calendar、trends24、Tier 1 の投稿 |

- **配信プラットフォームは元の媒体で数える。** Yahoo!ニュース・ライブドア・Infoseek・nippon.com は転載が多いので、「（元: SmartFLASH）」のように元媒体を書く。共同通信が配信して複数の地方紙に載った記事は1件と数える。
- C どうし（Yahoo!まとめ＋posfie など）は、どちらもXが源なので**独立した2件とは数えない**。

### 7-2. 裏取りの判定

| 判定 | 条件 | 選べるか |
|---|---|---|
| **確認済** | A/B が1件以上あり、独立したソースが計2件以上。出来事の内容が一致している | ○ |
| **条件付き** | C でバズは確認できたが、A/B は背景情報（古い記事・関連する発表）しかない | △（脚本では、確認済みの事実だけを前提にする。実在の人物・企業の言動や出来事そのものが核の場合は選ばない。作品の考察ブームやミームのような「現象」なら可） |
| **未確認** | C だけ／ソースが1件だけ／内容がソース間で食い違う／URLが取れていない | ×（落選欄に回す） |

- **追加条件**: 実在の人物・企業の**ネガティブな出来事**（不祥事・炎上・失言・事故・トラブル）が核になっている話題は、A/B を**2件以上**（独立した媒体）そろえて初めて「確認済」とする。足りなければ未確認として落とす（guardrails.md の R5 に当たるため）。

### 7-3. 日付の確認（どれか1つでなく、可能な限り全部見る）

1. **URLの中の日付**: `j-cast.com/2026/10/12...`、`sakigake.jp/news/article/20261002...`、`daily.co.jp/baseball/2025/10/12/...`（← **去年の記事**）
2. **タイトルの中の日付**: `(2026年10月11日掲載)`（ライブドア）、`(2026/10/12)`（Yahoo!まとめ）、`2026/10/11の話題ツイートまとめ`（posfie）
3. **Yahoo!まとめの URL 末尾**: Unix 秒（5-4）
4. **毎年ある行事の罠**: CS・ドラフト・紅白・M-1・ハロウィン・ノーベル賞などは、**去年の同じ行事の記事が先に出やすい**（実測で「巨人 CS 敗退 DeNA」を検索したら 2025-10-12 の記事が最上位だった）。
5. WebSearch の要約文に書かれた日付は証拠にしない。

### 7-4. 鮮度ラベル

- `[新鮮]` 最新の動きが**72時間以内**
- `[継続]` 初出は72時間より前だが、72時間以内に新しい展開（続報・二次バズ・パロディの連鎖）がある。上限は初出から7日程度
- `[古い]` それ以外。原則として落とす（Tier 0 のユーザー指定だけは例外）

## 8. ソースの記録ルール

- **ツールの出力に実際に出た URL だけ**を、そのまま記録する。URL を推測したり組み立てたりしない（4-2 の取得先の型を使って WebFetch が成功した場合だけ例外）。

  （クラス｜媒体（元媒体）｜記事の日付｜タイトルそのまま｜URL｜取得日と経路）
- 候補リストは、プロジェクトルートの **`parody-scripts/candidates/YYYY-MM-DD-candidates.md`** に保存し（同じ日に2回目以降なら `-2` などを付ける）、選んだ脚本ファイルのメタ情報からこのファイルを参照する。
- 除外ログ（カテゴリコード×件数）と落選ログ（話題名と理由）も同じファイルの末尾に残す。**除外（A〜H）した話題の名前・URL・人物名は書かない。**

```markdown

- なぜバズってる: <事実だけ。確認済みでない数値は書かない>
- 日付: 初出 YYYY-MM-DD / 最新の動き YYYY-MM-DD（鮮度ラベル）

  - [C] …
- 裏取り: 確認済／条件付き／未確認（理由）

```

### 9-3. 並べる順番

1. 選べるもの（確認済 → 条件付き）を、鮮度 → バズの強さ → パロディにしやすさの順に並べる。
2. そのあとに未確認（選べないもの）を、落選理由つきで並べる。

## 10. 初期のパロディ角度の付け方（候補表用の短い版）

- 型: 「実は裏で〜が起きていた」「〜の会議室では〜」「〜側の視点から見ると〜」
- **刺す相手**: 権力・企業・制度・状況の不条理、有名人の**公的な**言動、そして自分たち（視聴者やネット民の群れ）
- **刺さない相手**: 被害者・遺族、一般人、属性で区切った集団
- **明らかに作り話だと分かるくらい荒唐無稽にする**（タイムマシン、ソーセージの労働組合、ハッカーの社員旅行など）。現実にありそうな不正（「実は社長が横領」など）は書かない。
- 裏の物語の舞台・黒幕に実在の企業名・人物名を使わない（「メーカーの会議室」「某球団の監督室」のように役職・業種に落とす）。
- 数値・発言の引用は、裏取りが確認済みのものだけ使う。
